Factory Inventory Management System

Architecture overview: system design, tech stack, and data flow

System Architecture

A single-page Vue app talks to a stateless FastAPI service over REST. There is no database; JSON files are loaded into memory at startup.

Tech Stack

Runtime dependencies are intentionally small.

Frontend

  • Vue 3 (Composition API)
  • Vue Router 4
  • Axios
  • Vite 8 dev server and build
  • Custom SVG charts, CSS Grid layouts
  • English and Japanese locales

Backend

  • Python 3.11+
  • FastAPI
  • Uvicorn (ASGI server)
  • Pydantic v2 validation
  • uv for dependency management

Data

  • JSON files in server/data/
  • Loaded once by mock_data.py
  • Seed script: generate_data.py
  • No database; changes are not persisted

Tooling

  • pytest + FastAPI TestClient
  • Backend tests in tests/backend/
  • Claude Code agents, skills, and MCP config in .claude/

Data Flow

How a filter change on screen becomes updated data.

  1. User changes a filter FilterBar updates shared refs in useFilters (Time Period, Warehouse, Category, Order Status). The refs are module-level singletons, so every view sees them.
  2. View builds a request A watcher calls getCurrentFilters() and passes the result to a method in api.js. Values equal to all are omitted from the query string.
  3. FastAPI receives the query For example GET /api/orders?warehouse=...&category=...&status=...&month=Q3-2025. CORS is open to all origins.
  4. In-memory filtering apply_filters matches warehouse, category, and status. filter_by_month expands quarters (for example Q3-2025) into months and matches on order_date.
  5. Aggregation and validation Endpoints such as /api/dashboard/summary compute totals (inventory value, low-stock count, pending orders). List endpoints are validated through Pydantic response models.
  6. View renders Raw responses are stored in refs; derived values and chart data live in computed properties, so the UI updates reactively.

Known gap

client/src/api.js calls /api/tasks (GET, POST, PATCH, DELETE) and /api/purchase-orders (POST, GET), but server/main.py does not define these routes. Requests from the tasks and purchase-order features will return 404 until the endpoints are added. A CreatePurchaseOrderRequest model exists in the backend, and /api/backlog already reads purchase orders to set has_purchase_order.
